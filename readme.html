The engine, end to end

Two parts: a static web app (this site) that predicts matches live in the browser, and a Python pipeline that trains, calibrates, and backtests the model. The app's player data refreshes daily; the pipeline is where you prove the edge.

Run the web app

The app is fully static — no build step. Serve the folder and open it:

  1. Keep index.html, model-math.html, readme.html, styles.css, and players.json in one folder.
  2. On Replit, use a static/HTML Repl and press Run; locally, any static server works (e.g. python -m http.server).
  3. Serving matters: the app fetches players.json, which browsers block over a bare file:// path. Opened as a file it still runs — it just falls back to the built-in seed data.

The model, and how well it does

One implementation (model.py) is used by the daily updater, the match list and the backtest; the predictor repeats the same formula in the browser.

  • Rating: Elo on match results (walkovers and retirements skipped), with K = 150/(matches+5)0.6, so a rating moves fast early and settles quickly. Each surface is an offset on top of the overall rating. New players start at 1500, or 1250 if their first match is in qualifying and 1100 if it is at Challenger level.
  • Serve model: share of serve and return points won, weighted by recency (half-life 60 days), adjusted for the strength of each opponent, and pulled lightly toward the tour average when a player has few points. Fed through a point → game → set → match Markov chain.
  • Combination: a logistic-regression stack per tour on the log-odds of the Elo and serve-model probabilities, plus how thin each player's data is (few serve points, few rated matches), a big server vs elite returner term, layoff and fatigue. For a player with almost no rated matches the stack all but ignores Elo (their rating is still just the starting value) and leans on the serve numbers.

Backtest. tools/backtest.py predicts every saved match using only the matches before it. All settings were tuned together, on the finished prediction, over 2025-04-01 – 2026-03-31; the numbers below are the holdout (2026-04-01 – 2026-10-18, 5,010 finished ATP/WTA matches the tuning never saw).

Where the gain comes from: players new to the data. With no earlier match, holdout log loss went 0.698 → 0.481 (92 matches); with one or two, 0.585 → 0.528. On established players it is unchanged (0.614). The previous settings were under-confident between 60% and 90%; that is fixed. The very top end is a little over-confident (95%+ picks won 91% of 57 matches): too few to fit, and capping the probability made the tuning year worse, so treat 95%+ numbers with care.

Tested and not adopted:

  • Margin of victory in Elo (share of games won): no gain; the serve model already sees how dominant a win was, point by point.
  • Best-of-5 Elo (Elo's chance converted through the per-set chance): +0.0002.
  • Per-surface serve baselines: they shift both players' hold rates together, which cancels out in who wins.
  • Glicko-2: a tie with Elo. Court speed: when a court is fast both players hold more, which barely changes who wins.
  • Tuning only on the six settled months (2025-10 – 2026-03): it chose the same settings but the stack overfitted the smaller sample (holdout 0.6140).
  • Seeding from rankings: the saved match data has no historical rankings, so it can't be backtested.

More history. The saved results start 2024-09-30 and the ratings take about a year to settle (log loss 0.68 in the first months, 0.61 a year later). The daily update now extends the history back to 2022. Once it has, re-tune with python tools/backtest.py --tune (about 10 minutes): the settings above were chosen for the shorter history.

Against the bookmakers. tools/market_backtest.py joins every walk-forward prediction with the real pre-match prices (api-tennis, saved daily by tools/fetch_odds.py in data/odds_history.csv; they agree with the prices the site logged before each match). On 12,410 holdout matches:

Log loss
Model0.620
Bookmakers' de-vigged average0.579
Pinnacle (where it priced the match)0.582

The market is far sharper, and betting the model's own "value" lost about 7% per bet at every threshold, tour and level (90% intervals entirely below zero). Fitted on 19,000 earlier matches, a blend of market and model gives the model a weight of about 0.02: it knows nothing the prices don't. So value bets, Kelly stakes and parlays now use the betting probability (model.bet_prob): the bookmakers' consensus, stretched slightly (it is a little too timid), plus that sliver of model. A value flag now mostly means one bookmaker is offering more than the fair price. On the holdout that rule returned +2.0% on 5,176 bets (90%: −0.5% to +4.7%), and +13% on the 697 bets with a 3%+ edge (−2% to +30%): promising, not proven, and soft bookmakers limit accounts that win this way. The model's own percentage is still shown. Refit with python tools/market_backtest.py --write.

The live track record is the real test. On the first 608 settled live picks (model-based value bets) the market (log loss 0.621) beat the model (0.641); picks logged from now on carry the betting probability, and the record judges them on it.

Warnings. The match list flags: fewer than 10 matches in 12 months, more than 45 days since the last match, fewer than 3 matches on the surface this year, clay or grass specialists (half their matches on that surface), a retirement in the last 60 days (or two in six months), and model and market more than 15 points apart. The track record splits out value bets that carried no warnings, and compares the model with Pinnacle where Pinnacle prices the match.

Daily data updates

The app reads players.json on every load (uncached). update_data.py rebuilds it each morning, trying these sources in order for each tour:

  1. api-tennis.com (needs the TENNIS_API_KEY secret): ATP and WTA results with serve points won. Results are saved in data/api_tennis_matches.csv. The first run downloads about two years; after that each run fetches the last week and spends any time left extending the history back to 2022 a few weeks at a time (older results let the ratings settle before the matches being predicted). The saved history keeps working even if the subscription lapses.
  2. Jeff Sackmann's match files on GitHub: results plus serve/return stats (no longer available at the time of writing).
  3. tennis-data.co.uk yearly spreadsheets: results only. Elo stays current; serve/return stats are carried over from the previous day (new players get the tour average).
  4. Neither reachable: yesterday's file is kept and the Predictor's date stamp turns orange ("not updating"), so the site keeps working. The same happens if the newest result is more than two weeks old.

How the stats are built: a player is listed if they played in the last 12 months. Elo ignores walkovers and retirements. Serve/return rates count every point, weight recent matches more (a match a year old counts half), and are adjusted for opponent strength (points won against strong opponents count for more).

python update_data.py            # last 3 seasons
python update_data.py --top 60   # cap players per tour
python update_data.py --local atp_matches_2025.csv   # offline test, Sackmann format
python update_data.py --local-xlsx 2025.xlsx         # offline test, tennis-data format

Today's matches & live odds

update_matches.py pulls upcoming ATP and WTA matches (next 36 hours) with bookmaker odds from The Odds API, runs each one through the same model as the Predictor, and writes matches.json: model win chance, best price and which book has it, EV and a quarter-Kelly stake. The Predictor shows it as Today's matches; Analyse loads a match, its surface, format and odds.

The odds feed only lists matches a bookmaker has already priced, so the next day's order of play is often only partly there. With TENNIS_API_KEY set, the updater also reads the full schedule from api-tennis.com and adds the matches the odds feed doesn't have, with the model's chance and fair odds and a "no odds yet" note. Their prices fill in at the next refresh after bookmakers post them. These matches aren't logged to the track record or used in parlays until they have odds.

For those matches the updater also asks api-tennis.com for bookmaker odds (its get_odds, if your plan includes it), which covers qualifying and smaller events. A match priced this way gets EV, warnings and a place in the track record like any other, marked "odds via api-tennis"; if the odds feed prices it later, that price replaces it (and any logged parlay leg follows it to the odds feed's match, so it still settles). They can be legs in recommended parlays like any other match.

ODDS_API_KEY=your-key python update_matches.py
ODDS_API_KEY=your-key python update_matches.py --hours 48 --regions eu,uk

Surface comes from a built-in table of every ATP tournament: Grand Slams, Masters 1000, 500s, 250s and team events, plus the main WTA-only stops. Stuttgart is grass for ATP and clay for WTA. Indoor events are labelled but the model treats them as ordinary hard courts. A tournament not in the table counts as hard court and shows a “?” on the site. Only men's Grand Slams are best of 5. Players not in players.json — usually qualifiers — are listed under unmatched and skipped.

Track record

Every match in the daily list is logged to history/predictions.csv with the model's number, the market's number (margin removed) and the best price, updated with the last price seen before the start. Once a result appears in recent_results.json it's settled (walkovers are voided, as is anything with no result after 30 days). The Predictor's Track record panel shows how often the model picked the winner versus the bookmakers' favourite, an accuracy score (Brier; lower is better; if the market's is lower, the market is sharper than the model), and the profit from betting 1 unit on every value flag. Results arrive when the stats source publishes them, so settling can lag by days.

Scorelines

The predictor's Most likely scorelines panel shows the chance of each set result (2–0, 2–1, …) and the most likely full scores, with the games of every set (e.g. 6–4 3–6 7–6). The set results are solved so they add up to the headline win chance. Sets aren't quite independent: whoever wins a set is a little more likely to win the next, so there is a set momentum setting per tour and format, fitted on real set scores by python tools/backtest.py --sets (and --tune) and adopted only if it beats independent sets on the tuning year. The games inside each set come from the serve model playing the set game by game, nudged to agree with the set chances. Set and game scores are stored with each cached match; the first daily run after this change re-downloads the history once to add them, and the backtest then reports how the first-set game scores compare with reality.

Recommended parlays

Up to three 2- or 3-leg parlays live at a time, built only from upcoming matches with no warnings. A posted parlay stays on the predictor, unchanged and at its logged price, until its first match starts; then it moves to Past predictions and the next refresh fills the slot with a new ticket from matches that haven't started (no match in more than two live tickets). Each leg must be at least +3% EV at the parlay's bookmaker and have a 40%+ chance by the model, and the whole ticket at least +5% EV. Every ticket is priced at one bookmaker that offers all its legs, because prices from different books can't be combined into one bet. Legs are treated as independent (different matches). Each recommendation is logged to history/parlays.csv at the price first shown and settled from the match results (a void leg counts as odds 1.0); the site shows how many won against how many the model expected. A parlay multiplies the bookmaker's margin and any model error, so it needs a real edge on every leg; until the single-pick track record shows the model beats the market, treat these as entertainment-sized stakes.

Challengers (ATP Challenger, WTA 125)

The updater also keeps api-tennis.com's Challenger singles (men's ATP Challenger and women's WTA 125) in the match cache, two years back. The history arrives over the first few daily runs, since each run spends at most 18 minutes on it and saves as it goes. Challenger results go into the same rating pool as the tour, so a player's Challenger form counts toward their ATP or WTA rating. That matters most for qualifiers, who play mostly Challengers. How much a Challenger match counts (ch_k for the rating, ch_sv for serve points) and where a player first seen at Challenger level starts (init_elo_ch) are picked by tools/backtest.py --challenger on the tune period, scored on the same tour-level matches as before. They're switched on only if they improve those predictions (ch_use). Once they're on, Challenger matches appear in the match list as "ATP Challenger …" or "WTA 125 …" with api-tennis and Kalshi prices, under their own tabs.

Challenger surfaces come from api-tennis's own tournament data when it has them, otherwise from a list of hosts that always use one surface. Anything else shows "surface?" and is treated as hard. Expect the model to be less sure at this level: players change more, and prices move more.

Kalshi

The updater also reads Kalshi's public tennis match markets (no key needed) and pairs them with the match list by player names. Each player's contract costs 1–99¢ and pays $1 if they win; the site shows that price, the decimal odds after Kalshi's trading fee (about 7% × p × (1 − p) per contract), the EV at that price, and a link to the market. Kalshi gets its own three live parlay slots, rolling the same way, built with the same rules as the bookmaker ones but priced at Kalshi, and logged and settled the same way. Kalshi builds multi-leg bets ("combos") in its app, so each leg links to its market; the ticket price on the site multiplies the legs' prices, and Kalshi's own combo quote may differ a little. Kalshi is also one of the choices in the parlay builder.

Parlay builder

On the predictor, the + next to each player in Today's matches adds that player to the parlay builder (one side per match, up to ten legs); a recommended parlay can be opened there too. Choose a bookmaker that prices every leg (listed best combined price first), the best price for each leg (which mixes books, so it can't be placed as one ticket), or type your own prices. The builder multiplies the prices and the model's chances, and shows EV, a quarter-Kelly stake and the return on your stake. Legs are kept in your browser only; builder tickets aren't logged.

Past predictions

The Past predictions page shows the prediction log one day at a time, with the result, whether the model was right and the value-bet profit, plus filters and a search across every day.

Automatic daily run (one-time setup)

.github/workflows/update.yml runs every day at 06:20 UTC. It rebuilds the player stats, the match list and the track record, commits them, and publishes the site to GitHub Pages. Runs at 16:20 and 21:20 UTC refresh only the odds (bookmakers often price the next day in the evening), and skips them if fewer than 60 requests are left in the month. In every other hour, a quick run at :35 refreshes the order of play (Challenger matches appear once each event publishes it, usually the evening before), the api-tennis odds and Kalshi. It keeps the main odds feed's last prices, so it doesn't use that feed's monthly allowance, and the site notes when those prices are from. If api-tennis doesn't answer, the last list is kept. GitHub sometimes starts scheduled runs hours late; the hourly runs keep the list current when it does. You can also run it by hand from the repo's Actions tab (refresh-data → Run workflow).

  1. Turn on Pages: repo Settings → Pages → Build and deployment → Source: GitHub Actions. The site appears at https://<user>.github.io/<repo>/.
  2. Add the stats key: from api-tennis.com, as a repository secret named TENNIS_API_KEY (same place as the odds key below).
  3. Add the odds key: sign up free at the-odds-api.com (500 requests a month; each run uses about one per active tournament, so around 300 a month), then add it under Settings → Secrets and variables → Actions → New repository secret, named ODDS_API_KEY. Without it everything else still updates and the match panel says the feed isn't connected.
  4. Let Actions push: Settings → Actions → General → Workflow permissions → Read and write permissions.

Odds move. Main-feed prices are snapshots from 06:20, 16:20 and 21:20 UTC; api-tennis and Kalshi prices are at most about an hour old. Check the live price before acting on any "value" flag.

The date stamps on the Predictor show when each file was last rebuilt.

Feed real data to the analysis pipeline

That's the app's data. The separate analysis pipeline (where you backtest and calibrate) ships running on synthetic data. To point it at real matches, grab Jeff Sackmann's ATP files (atp_matches_YYYY.csv) from github.com/JeffSackmann/tennis_atp, then in main.py replace:

df = generate_synthetic_matches()

with:

from data import load_sackmann_csv
df = load_sackmann_csv("atp_matches_2024.csv")  # or concat several years, sorted by date

Two things to fix for real data:

  • Sort chronologically before the walk — ELO must update in match order.
  • The loader sets player A = winner every row, so labels are all True. Shuffle each match's A/B assignment (and flip a_won) so the model trains on balanced outcomes.

Build order, if extending

ELO → logistic baseline → Markov → ensemble → calibrate & verify per-segment → backtest against closing lines with vig → de-vig live odds → fractional Kelly. A calibrated simple model beats an uncalibrated sophisticated one every time.

For real-money use: a real market is sharper than this simulation, edges are thin and decay, and no calibration holds forever — re-fit on a rolling window and treat responsible-gambling limits as core features.
